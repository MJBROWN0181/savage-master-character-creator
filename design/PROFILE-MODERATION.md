# Profile sharing and review

Each account has one profile with optional Player and Game Master roles. Personal fields are optional. The fixed handle is the share address; account email and age confirmation are never returned by the public query.

Age confirmation is an 18+ self-attestation, not independent identity or document verification. Do not describe it as verified identity. A stronger age assurance service can be added before opening profiles to younger users.

Completing first profile setup requires age confirmation and acceptance of the community rules. The first save automatically puts the profile in the pending review queue and schedules an email notification. Players see their review status on their own profile. Pending profiles remain private and cannot post in Chronicles until approved. Editing a pending profile keeps it queued; its changed revision invalidates any earlier review. Existing private drafts remain private when saved. Existing profiles can request review from Review & save, which hides any previously published version. Repeated pending requests are idempotent; resubmissions have a one-minute cooldown.

Email notices use the existing support/auth mail credentials. Set server-only `PROFILE_REVIEW_EMAIL_TO` to override the inbox; otherwise notices use the protected owner's verified email, then configured legacy reviewer/support inboxes. Each email has a Review profile button linking to `/profile-reviews?profile=ID`. No profile content appears in the email. `SITE_URL` determines the site. Delivery retries up to three times with an idempotency key. Missing configuration and failed delivery stay visible; Send review email repairs older pending profiles with no recorded notification or retries failure, with server cooldowns. The owner's email is read only inside internal server functions and is never returned to staff.

Reviewers open the separate private `/profile-reviews` workspace, available from reviewer Settings. Old `/profile?reviews=1` links remain compatible. Configure owner accounts using server-only `PROFILE_MODERATOR_ADMIN_EMAILS` (fallback: `BUG_EDITOR_EMAILS`, then `PROFILE_REVIEWER_EMAILS`). Configure other permanent reviewers with `PROFILE_REVIEWER_EMAILS`. All access requires a verified database email, never client identity claims. Account owners cannot approve their own profiles; the page explains this and disables their decision buttons. Review the text, imagery, links, selected portraits and excerpts for sexual/explicit imagery, hate, harassment, threats, scams, private information, and rights to uploaded material. Approval publishes the exact reviewed revision and enables Chronicles posting. Request changes requires a private note. Draft revision and submission time checks reject stale decisions.

The production build initializes the existing verified @warrior-king81 account as the protected owner using internal `moderation:initializeOwner`. Initialization is idempotent and cannot replace an established owner. There is no public self-promotion endpoint. Once initialized, the persistent owner record takes precedence over legacy email configuration.

The owner's Team & decisions panel grants or revokes Admin or Moderator access by gamer handle. Both roles can review profiles, track bug tickets, and pause member community access. Admins also receive the Admin frame. Only the owner can manage staff roles. Staff cannot access billing, passwords, contacts, or other users' private game data. Recent profile decisions identify the acting staff handle without account email or free-form private notes. No invitation email is sent: give a helper the private workspace link after adding them. Revocation is checked server-side on every request and removes the Admin frame.

Member accounts lists only the handle, verification flag, public review status, staff role, and community access state. Pausing community access hides the public profile, removes posting eligibility, and gates community services through their shared reviewed-profile policy. It preserves login, private sheets, and journals. Staff cannot change the owner account or themselves; only the owner can pause or restore another staff member. Changes are recorded in the internal moderation audit.

Bug reports lists system ticket identifiers, a fixed issue category, dates, and status. Staff can mark tickets open, in progress, or resolved. Original titles, messages, diagnostics, reply addresses, owner IDs, request identifiers, and replies are excluded because free-form reports may contain personal information. Original report details remain in the existing private support inbox/operator tools. New support submissions choose a fixed category; old tickets show Other. This privacy boundary means helpers cannot read the original bug description from this workspace.

Reported profiles shows the reviewed public version and report reasons, without revealing the reporting user's identity. Hide public profile removes public sharing and posting eligibility, saves the reason for the owner, and keeps their private data and account. Dismiss reviewed reports closes the inspected reports without altering the profile. Resolved reports retain the moderator and resolution; users can report a newly published problem after an earlier report was resolved.

Privileged Convex operators can still use `profiles:reviewQueue`, `profiles:moderate`, and `profiles:withdraw`. The app records decisions made through the reviewer workflow; internal operator actions remain outside that account attribution. Moderation is manual content review, not verified identity or automatic image scanning. Post, Guild and Bazaar moderation are separate systems; this workspace covers profiles.

Images are decoded and re-encoded as WebP in the browser to remove source metadata, capped in dimensions, and checked server-side by byte signature and file size. These checks protect file format handling; they do not detect offensive visual content. Uploads are limited to 20 registered profile images per day. Storage cleanup, stronger upload rate limits, and automated moderation are future operational improvements.

Only owned characters may be featured. Public character cards contain the name and chosen portrait, not their entire sheet. Only exact, explicitly selected excerpts from the user's player journals may be shared. GM journal entries cannot be featured. Public snapshots freeze reviewed content; edits to an approved profile do not silently change what visitors see. Shop/social links must use HTTPS and open separately with no opener access. Marketplace listings are linked by URL until the marketplace has real listing records.

The personal editor allows safe background/color/font/layout presets, a custom background image, and section ordering. It accepts no arbitrary HTML, script, or CSS. The profile avatar stays a fixed circular identity area; account controls remain outside the customized page.
